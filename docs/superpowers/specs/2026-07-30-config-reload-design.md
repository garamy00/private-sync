# agent 설정 자동 리로드 설계

작성일: 2026-07-30

## 배경

`private-sync` agent는 설정을 시작할 때 한 번만 읽는다
([agent/main.py](../../../src/private_sync/agent/main.py) `main()`의 `load_agent_config`).
감시 대상 목록은 `build_targets`로 그때 한 번 계산되고, `observer.schedule`도 그 시점에
한 번만 등록되며, `_EventHandler`와 `SyncWorker`가 각각 그 시점의 대상 목록과 exclude를
붙잡는다. SIGHUP 핸들러는 없다.

따라서 감시 목록을 바꾸려면 데몬을 재시작해야 한다. 동기화할 폴더를 추가하거나 exclude를
조정하는 일은 자주 생기는데, 그때마다 `launchctl kickstart`를 기억해서 쳐야 한다는 뜻이다.
잊으면 설정은 바뀌었는데 아무 일도 일어나지 않고, 그 사실을 알려주는 신호도 없다.

## 목표와 비목표

**목표** — `agent.yaml`을 저장하면 재시작 없이 반영된다. 반영 대상은 감시 경로 추가·제거,
라벨 변경, exclude 변경, remote 설정 변경이다.

**비목표**

- bot 설정 리로드. bot의 설정은 `store` 경로 하나와 환경변수 세 개뿐이고, 환경변수는 어차피
  서비스 재시작이 필요하다.
- 감시 대상 경로가 런타임에 생기거나 사라지는 상황의 처리. 지금도 설정 검증이 없는 경로를
  거부하며, 이 설계는 그 동작을 바꾸지 않는다.
- 서버 저장소 정리. 삭제는 전파하지 않는다는 기존 원칙을 유지한다.

## 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 감지 수단 | 설정 파일 mtime 폴링 (기존 1초 틱에 편승) | 에디터의 "임시파일 쓰기 → rename" 저장에도 안정적이다. watchdog으로 단일 파일을 감시하면 inode가 바뀌어 헛돈다 |
| 잘못된 설정 | 이전 설정 유지, ERROR 로그, 데몬 계속 실행 | 여기서 종료하면 launchd가 재시작하고 같은 설정으로 또 죽어 크래시 루프가 된다 |
| 새로 추가된 대상 | 초기 동기화 큐에 넣는다 | 넣지 않으면 새 폴더를 추가해도 건드리기 전까지 안 올라간다 — 방금 고친 문제의 재발이다 |
| 기존 대상 | 다시 큐에 넣지 않는다 | 설정을 저장할 때마다 전체를 훑을 이유가 없다 |
| 사라진 라벨 | 경고 로그만, 서버 파일은 그대로 | 오타 한 번으로 백업본이 사라지면 이 프로젝트의 목적과 어긋난다 |

## 동작

### 감지

`_run_loop`의 매 틱에서 설정 파일의 mtime을 확인한다. 직전에 본 값과 다르면 리로드를
시도한다. 파일이 사라졌으면 이전 설정을 유지하고 경고를 남긴다.

저장 도중에 읽혀 내용이 불완전하면 파싱이나 검증이 실패하는데, 이때 이전 설정을 유지한다.
저장이 끝나면 mtime이 다시 바뀌므로 다음 틱에서 자동으로 재시도된다. 별도의 안정화 대기
구간을 두지 않는 이유는 이 자체가 자기 교정이기 때문이다.

### 적용

새 설정을 읽어 검증한 뒤 네 가지를 함께 교체한다. 하나라도 빠지면 상태가 어긋난다.

1. `build_targets`로 감시 대상 재계산
2. observer의 watch 등록: `unschedule_all()` 후 새 대상으로 재등록
3. `_EventHandler`가 든 대상 목록 교체
4. `SyncWorker`의 remote 설정과 exclude 맵 교체

그다음 새 설정에만 있는 `(label, path)` 조합을 초기 동기화 큐에 넣고, 이전 설정에만 있던
라벨을 경고로 남긴다.

대기 목록에 남아 있던 사라진 라벨의 항목은 별도 처리가 필요 없다. `SyncWorker.drain`이
이미 알 수 없는 라벨을 폐기한다.

## 구조

```
ConfigWatcher(path)          설정 파일 mtime 변화만 판단한다. 시간을 주입받는다.
  .changed() -> bool

AgentRuntime                 리로드 시 함께 갱신되는 것들의 묶음.
  worker, handler, observer, config_path

_reload_config(runtime)      새 설정을 읽어 runtime 전체에 적용한다.
                             실패하면 False를 반환하고 아무것도 바꾸지 않는다.

SyncWorker.replace_config()  remote 설정과 exclude 맵을 교체한다.
_EventHandler.replace_targets()  감시 대상 목록을 교체한다.
```

`AgentRuntime`으로 묶는 이유는 `_reload_config`가 갱신해야 할 대상이 넷이기 때문이다.
개별 인자로 넘기면 파라미터 3개 이하 규칙을 넘긴다.

`_run_loop`은 `(runtime, state)` 두 인자를 받게 바뀐다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 설정 파일 삭제됨 | 이전 설정 유지, WARNING |
| 파싱·검증 실패 (오타, 없는 경로, 저장 중 읽힘) | 이전 설정 유지, ERROR, 다음 mtime 변경 시 재시도 |
| 리로드 성공 | INFO로 대상 수와 추가·제거된 라벨을 남긴다 |
| observer 재등록 실패 | CRITICAL 후 데몬 종료 |

설정 실패는 살아남고 observer 실패는 죽는 것이 모순처럼 보이지만 상황이 다르다. 설정
파싱 실패는 사용자의 오타이거나 저장 중에 읽힌 것이고, 고쳐서 저장하면 저절로 회복된다.
반면 observer 재등록 실패는 이전 등록을 이미 해제한 뒤에 일어나므로 감시가 하나도 없는
상태로 남는다. 그대로 돌면 데몬은 정상인 척하면서 아무것도 동기화하지 않는다 — 이
프로젝트가 이미 두 번 당한 조용한 실패다. 시끄럽게 죽는 편이 낫다.

## 테스트

- `ConfigWatcher`: 첫 호출은 변경 없음, mtime이 바뀌면 감지, 같은 값이면 반복 감지하지 않음, 파일이 없으면 예외 없이 False
- 리로드 후 새 라벨이 감시 대상에 반영되는지
- 잘못된 설정에서 이전 설정이 유지되고 예외가 새지 않는지
- 새로 추가된 대상만 초기 동기화 큐에 들어가고 기존 대상은 다시 들어가지 않는지
- 사라진 라벨에 대해 경고가 남는지
- 리로드 시 observer가 `unschedule_all` 후 재등록되는지 (가짜 observer로 호출 순서 확인)

## 범위에서 제외

bot 설정 리로드, 감시 경로의 런타임 생성·삭제 추적, 서버 저장소 정리, SIGHUP 지원.
