# 폴더 압축 다운로드와 대형 목록 처리 설계

작성일: 2026-08-03

## 배경

봇으로 폴더를 눌렀을 때 아무 반응이 없다는 보고가 있었다. 서버 로그에 원인이 그대로 남아 있었다.

```
2026-08-03 12:16:37 ERROR private_sync.bot.main
  Failed to deliver text response: editMessageText returned status 400
```

해당 폴더에는 항목이 201개(MP3 100 + LRC 100 + 하위 디렉토리) 있었다. `_browse`는 항목마다
버튼을 하나씩 만들므로 202개짜리 인라인 키보드를 보냈고 텔레그램이 400으로 거부했다.
`Deliverer._send_text`는 `TelegramError`를 잡아 로그만 남기므로 사용자에게는 아무 일도
일어나지 않은 것처럼 보인다. 봇은 정상 동작 중이었다.

두 번째 요구는 폴더를 통째로 압축해 받는 것이다. 지금은 파일 하나씩만 받을 수 있다.

## 사실 확인

텔레그램 공식 문서로 확인했다.

- 표준 Bot API: 봇의 파일 업로드 한도는 50MB.
- 로컬 Bot API 서버: "Upload files up to 2000 MB", "Download files without a size limit",
  그리고 "Upload files using their local path and the file URI scheme".

마지막 항목이 중요하다. 봇과 API 서버가 같은 장비에 있으면 파일을 HTTP로 밀어 넣지 않고
경로만 넘길 수 있다. 843MB 파일을 우리 프로세스에서 한 번 더 퍼내는 과정이 사라진다.

대상 폴더는 843MB다. 표준 API로는 45MB × 19파트, 로컬 서버로는 파일 하나다.

## 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 파일 크기 한도 | 로컬 Bot API 서버 도입 | 19파트를 받아 PC에서 `cat`으로 합치는 절차는 실사용에서 쓰이지 않는다 |
| 큰 폴더를 눌렀을 때 | 크기·개수·예상 파트 수를 먼저 보여주고 확인받는다 | 실수로 843MB 전송을 시작하면 되돌릴 수 없다 |
| 압축·전송 중 봇 응답 | 순차 처리하고 진행 상황만 알린다 | 동시에 둘을 받을 일이 없다. 백그라운드 스레드는 공유 상태와 취소 처리를 불러온다 |
| 대형 목록 | 페이지네이션 | 상한을 두고 자르면 뒤쪽 파일에 영영 닿을 수 없다 |
| 전송 실패 | 사용자에게 알린다 | 지금은 로그만 남아 "눌러도 반응 없음"으로 보인다. 이번 증상의 절반이다 |
| 구현 순서 | 1 → 2 → 3 | 1은 그 자체로 막힌 것을 뚫고, 3은 2 없이는 실용성이 없다 |

## 1. 대형 목록

`_browse`가 만드는 버튼을 페이지로 나눈다. 한 화면에 20개, 아래에 `◀ 이전` `n/N` `다음 ▶`을
붙인다.

페이지 위치는 `TokenMap`에 함께 담는다. 지금 `(kind, rel)`을 저장하는 것을 `(kind, rel, page)`로
넓히고 `page`는 기본 0으로 둔다. `callback_data`에는 여전히 토큰만 실리므로 경로도 페이지도
밖으로 새지 않는다. 페이지 이동 버튼은 같은 `rel`에 다른 `page`를 가리키는 토큰을 새로 발급한다.

`⬆️ 상위`는 첫 페이지에만이 아니라 모든 페이지에 둔다. 깊이 들어간 뒤 3페이지에서 되돌아갈 수
있어야 한다.

**전송 실패를 사용자에게 알린다.** `Deliverer._send_text`가 `TelegramError`를 잡으면 로그만
남기지 말고, 버튼 없는 짧은 안내를 다시 보낸다. 그마저 실패하면 그때는 로그만 남긴다(무한
재시도를 막는다).

## 2. 로컬 Bot API 서버

### 서버 쪽

DGX에 `telegram-bot-api`를 설치하고 systemd 유저 서비스로 등록한다. `my.telegram.org`에서
발급받은 `api_id`/`api_hash`가 필요하며, 이는 봇 토큰과 다른 종류의 비밀값이다 — 봇 하나가
아니라 계정에 묶인 앱 자격증명이므로 `bot.env`(mode 600)에만 둔다.

### 봇 쪽

두 가지만 바뀐다.

**베이스 URL을 설정에서 받는다.** `PRIVATE_SYNC_API_BASE`, 기본값 `https://api.telegram.org`.
미설정이면 지금과 동일하게 동작하므로 로컬 서버 없이도 그대로 쓸 수 있다.

**로컬 경로 업로드.** 로컬 서버를 쓸 때 `sendDocument`에 multipart로 파일을 싣지 않고
`file://` 절대경로를 넘긴다. API 서버가 파일을 직접 읽으므로 같은 장비여야 하고, 그 프로세스가
읽을 수 있는 권한이어야 한다(둘 다 `dgson`으로 돌므로 충족된다). 베이스 URL이 기본값이면 기존
multipart 경로를 쓴다.

**분할 단위도 설정값으로 뺀다.** `PRIVATE_SYNC_MAX_PART_MB`, 미설정 시 기본 45(표준 API의 50MB
한도에서 여유를 뺀 현재 값). 로컬 서버를 쓸 때 권장값은 1900으로, 문서상 한도 2000MB에서 같은
비율의 여유를 남긴 값이다.

**시작 시 베이스 URL 도달 가능 여부를 확인한다.** 로컬 서버가 죽어 있으면 봇이 통째로 먹통이
되므로, `getMe` 한 번으로 확인하고 실패하면 명확한 메시지와 함께 종료한다. 조용히 도는 것보다
낫다.

## 3. 폴더 압축 다운로드

폴더 탐색 화면 맨 위에 `📦 이 폴더 통째로 받기` 버튼을 둔다.

누르면 바로 압축하지 않고 확인 화면을 보여준다 — 총 크기, 파일 개수, 예상 파트 수, 그리고
`[받기]` `[취소]`. 크기 계산은 하위 전체를 훑으므로 큰 폴더에서 시간이 걸릴 수 있다. 이때도
심볼릭 링크는 저장소 탐색과 같은 규칙으로 제외한다(`_resolves_inside`).

`받기`를 누르면 같은 메시지를 편집해가며 진행 상황을 갱신한다.

```
압축 중… (843MB)
전송 중…
완료
```

새 메시지를 쌓지 않는 이유는 폰에서 스크롤이 지저분해지기 때문이다.

**압축 전에 디스크 여유를 확인한다.** 필요량의 1.1배가 없으면 시작하지 않고 알린다. 임시 zip은
지금처럼 성공·실패와 무관하게 `finally`에서 지운다.

압축은 기존 `packer`를 재사용하되 디렉토리를 받을 수 있게 확장한다. 암호화는 파일과 동일하게
AES-256을 유지한다.

## 에러 처리

| 상황 | 동작 |
|---|---|
| 목록이 커서 `editMessageText` 400 | 페이지네이션으로 애초에 발생하지 않게 하고, 그래도 실패하면 안내 메시지 |
| 로컬 API 서버 미기동 | 시작 시 `getMe` 실패 → 명확한 메시지 후 종료 |
| 디스크 부족 | 압축 시작하지 않고 필요량·여유량을 알림 |
| 압축 중 오류 | 임시 파일 정리 후 안내 |
| 전송 중 오류 | 몇 번째 파트에서 끊겼는지 알린다(기존 동작 유지) |
| 확인 화면의 토큰 만료 | "목록이 만료되었습니다" 안내(기존 동작) |

## 테스트

커버리지 수치를 위한 형식적 테스트는 만들지 않는다.

- 페이지네이션: 항목 수가 페이지 크기의 배수일 때·아닐 때 경계, 마지막 페이지, 모든 페이지에
  `⬆️ 상위`가 있는지, 토큰에 경로가 담기지 않는지
- 전송 실패 알림: `editMessageText`가 실패하면 안내가 나가는지, 그 안내마저 실패하면 조용히
  로그만 남는지
- 베이스 URL: 미설정 시 기존 URL이 그대로 만들어지는지, 설정 시 그 URL을 쓰는지
- 로컬 경로 업로드: 로컬 서버 설정일 때 multipart 대신 `file://` 경로를 보내는지
- 폴더 크기 계산: 심볼릭 링크가 제외되는지, 빈 폴더
- 디스크 여유 부족: 압축을 시작하지 않고 안내하는지
- 확인 → 받기 흐름: 확인 화면이 전송을 시작하지 않는지, `받기`를 눌러야 시작하는지

## 범위에서 제외

- 백그라운드 처리와 전송 취소
- 폴더 다운로드의 이어받기(중단되면 처음부터)
- 압축 형식 선택(zip 고정)
- 서버 → 노트북 역방향 동기화
